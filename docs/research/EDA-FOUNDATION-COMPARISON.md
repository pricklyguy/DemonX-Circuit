# Choose an engine without surrendering the workflow

**As of 2026-10-24, use a DemonX-owned workflow and manifest over a versioned engine adapter, with KiCad 10.0.7 as the first CLI-backed engine.** This keeps native EDA files accessible, exercises ERC/DRC, Gerber/Excellon and STEP, and leaves the product interface free to evolve independently. The hosted native fixture and LED smoke passed; this remains a feasibility fixture rather than a manufacturing-approved design. LibrePCB remains the strongest alternative to test as a second adapter; Horizon EDA and Fritzing are useful comparison points but have larger evidence or capability gaps for this use.

## KiCad currently leads on the required automation boundary

KiCad 10.0.7 is the stable version identified by upstream tags, with active 10.0 patch releases during 2026. Official downloads and build documentation cover Windows and Linux. Its editable project is a set of native `.kicad_pro`, `.kicad_sch`, `.kicad_pcb` and library files. Keep those files as the authoritative circuit and board data; parse only through version-aware adapters and prefer documented CLI outputs over direct S-expression mutation. ([KiCad tags](https://gitlab.com/kicad/code/kicad/-/tags), [downloads](https://www.kicad.org/download/), [build documentation](https://dev-docs.kicad.org/en/build/), [10.0 manual](https://docs.kicad.org/10.0/en/))

The documented `kicad-cli` boundary covers schematic ERC, PCB DRC, Gerber and drill generation, and STEP export. Drill output can be Excellon or Gerber X2; STEP can include the assembly, with origin and virtual-component options. The documented Pcbnew Python API can inspect and manipulate PCB objects, but it is tied to the installed build and is not a stable remote editing contract. No corresponding supported Eeschema Python editing API or official MCP server was found. Therefore the first adapter should call a pinned CLI, parse its reports, and launch the native editor for canvas work; editing through undocumented APIs remains explicitly unsupported. ([CLI 10.0](https://docs.kicad.org/10.0/en/cli/cli.html), [Python API 10.0](https://docs.kicad.org/doxygen-python-10.0/))

Official symbols, footprints and 3D models are separate repositories, and licenses must be reviewed per library and asset. This is a mature, broad ecosystem but not a blanket permission to redistribute every component. Community collections and third-party parts should retain provenance and license metadata in the DemonX-owned library index. ([symbols](https://gitlab.com/kicad/libraries/kicad-symbols), [footprints](https://gitlab.com/kicad/libraries/kicad-footprints), [3D packages](https://gitlab.com/kicad/libraries/kicad-packages3D))

## LibrePCB merits a fixture-based second opinion

LibrePCB 2.1.1 (2026-06-12) ships official Windows and Linux packages. Its project and semantic library model are text-based and versioned, with components, symbols, devices, packages and footprints kept distinct; project files use `.lpp`/`.lppz`. The official base library is listed as CC0, though each other library needs its own review. The official CLI opens projects, runs ERC/DRC and executes output jobs, including Gerber/Excellon in the manual examples. The available evidence did not confirm Gerber X2 or assembled STEP export for 2.1.1. CLI is automation for checking and output, not a general editing API; direct native-format writes require schema-aware validation. ([release files](https://download.librepcb.org/releases/2.1.1/), [source](https://github.com/LibrePCB/LibrePCB), [CLI manual](https://librepcb.org/docs/librepcb-documentation.pdf), [libraries](https://github.com/LibrePCB-Libraries))

LibrePCB's owned, semantic library model and approachable interface make it a credible product foundation, especially if component ownership and beginner workflow dominate. For this first integration, KiCad has the better evidence for a complete automated output chain including STEP and broader library ecosystem. Before locking the engine long-term, run the same project fixture through LibrePCB and compare component coverage, unattended edits, rule reports and fabrication outputs.

## Horizon and Fritzing have narrower evidence for this role

Horizon EDA's latest release surfaced in the reviewed release page is 2.7.2 “Mirage”; its exact release date and support cadence were not established. It uses C++, Gtkmm3, OpenGL and JSON data with UUID references, and supports Windows and Linux. CLI, Python and parameter-program documentation make automation plausible, but direct writes still depend on schema and UUID invariants. Exact ERC scope, Gerber X2/Excellon options and STEP assembly export were not confirmed in the reviewed material. Its smaller ecosystem and less visible release cadence increase adoption risk. ([releases](https://github.com/horizon-eda/horizon/releases), [source](https://github.com/horizon-eda/horizon), [CLI documentation](https://github.com/horizon-eda/horizon-docs/blob/master/cli-usage.rst))

Fritzing is a useful beginner-oriented asset migration candidate: it has editable SVG/FZP parts and a server mode. Its app is GPLv3, while part assets have separate CC BY-SA 3.0 terms. The research did not establish professional-grade ERC/DRC or STEP assembly export; the current stable version also needs confirmation from official release channels before selection. It should not be the core verification/manufacturing engine. ([part format](https://github.com/fritzing/fritzing-app/wiki/2.1-part-file-format), [server mode](https://github.com/fritzing/fritzing-app/wiki/3.1-Running-fritzing-as-a-server), [source and license](https://github.com/fritzing/fritzing-app))

## The interface should compose engines instead of forking one

Forking KiCad or another EDA provides full canvas control but couples DemonX UX to internal code and carries long-lived upstream divergence and copyleft obligations. A fresh EDA built from libraries offers full brand control but requires DemonX to reproduce semantic design, robust ERC/DRC, routing, fabrication and 3D output before it can earn manufacturing trust. A DemonX workflow layer with native editor launch and isolated adapters gets the shortest reliable path: guides, project/library ownership, approvals, MCP, exports, Forge handoff and ESPHome generation can be built around an engine that already produces standard artifacts.

The Checkpoint 3 native smoke now exercises generation/reopening, 0-error/0-warning ERC, named net checks, 0-violation/0-unconnected-pad DRC before and after reopen, Gerber X2/Excellon/STEP export and a native user-library export/delete/reimport/reuse round-trip. These results support KiCad as the provisional engine, not final engine selection or manufacturing readiness. Key open questions remain library breadth and per-asset redistribution rights, versioned project parsing, board/STEP orientation into Forge, and Gerber-to-CNC accuracy. No official KiCad, LibrePCB or Horizon MCP integration was found in the reviewed upstream documentation; Codex/Claude interoperability remains untested.

## Conclusion

Keep the first contract narrow: native KiCad files plus a manifest, pinned CLI checks and outputs, and an adapter boundary that permits a LibrePCB comparison. This preserves the option to replace the engine on evidence, while DemonX can begin proving the cross-suite experience without rebuilding CAD canvases.
