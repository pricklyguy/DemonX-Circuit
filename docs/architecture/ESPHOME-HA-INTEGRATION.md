# Generate firmware from explicit hardware evidence

Circuit should generate editable ESPHome YAML from verified connectivity plus user-supplied behavior, then validate it with a pinned ESPHome CLI. A schematic alone does not specify relay polarity, sensor settings, Wi-Fi, entity names, update intervals or safe state. Missing decisions must remain marked placeholders or become questions; AI suggestions are never treated as electrical verification.

## Initial YAML workflow

Generate into a new project staging file and show a diff. Include substitutions, optional local packages/includes, API encryption, OTA, fallback AP, captive portal and web server only as user-selected features. Keep credentials in a local secrets file excluded from source control and MCP responses. Never silently overwrite an existing YAML; back it up and obtain approval after comparison. Use argv-based process invocation in a constrained working directory.

Check the exact tool with `esphome version`, run `esphome config <file>` for schema validation, and offer `esphome compile <file>` for compiler validation when available. Record version, board/chip profile, toolchain, warnings and exit status. Validation proves configuration acceptance; compilation does not prove wiring correctness or safety. The current research snapshot is ESPHome 2026.10.0, released 2026-10-21, with Device Builder 1.25.0 bundled. Device Builder is stable but independently versioned; use documented CLI as the automation boundary, not internal helper APIs as a remote contract. ([release](https://github.com/esphome/esphome/releases/tag/2026.10.0), [install](https://esphome.io/install/), [CLI](https://esphome.io/guides/cli/), [Device Builder](https://github.com/esphome/device-builder))

Templates should support substitutions/packages with pinned remote revisions, `api.encryption.key`, current OTA list syntax (`- platform: esphome`), optional `wifi.ap` and `captive_portal:`, and optional `web_server:`. Explain the security and reproducibility effect of each option. Do not include secrets in AI context, shared library records, public manifest or logs. Generated YAML and user templates remain editable and portable. ([substitutions](https://esphome.io/components/substitutions/), [packages](https://esphome.io/components/packages/), [API](https://esphome.io/components/api/), [OTA](https://esphome.io/components/ota/esphome/), [captive portal](https://esphome.io/components/captive_portal/), [web server](https://esphome.io/components/web_server/))

## Pin mapping must follow the real board

Store controller chip, module, board model/revision and source provenance with each pin mapping. Flag reserved pins, boot straps, input-only pins, ADC2-plus-Wi-Fi conflicts, voltage mismatch, bus conflicts and unresolved pin exposure. For original ESP32, GPIO0, 2, 5, 12 and 15 are strap pins; GPIO34+ are input-only without internal pulls; ADC2 conflicts with Wi-Fi. These rules are chip-specific and must not be copied to ESP32-C3/S3/C6 without their own sources. A generic `esp32dev` board ID is insufficient evidence for a physical custom board. ([Espressif hardware checklist](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32/schematic-checklist.html), [DevKitC guide](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32/esp32-devkitc/user_guide.html), [ESPHome ESP32 platform](https://esphome.io/components/esp32/))

The local fixture names ESP32-S3-WROOM-1-N8, maps GPIO8 to I2C SDA, GPIO9 to SCL and GPIO10 to a relay driver, and emits ESPHome's `esp32.variant: esp32s3` form. This is a candidate map for the reference native schematic. It is not yet a verified connectivity map or tested board design. Component candidates are now specified in [ESP32-REFERENCE-FIXTURE-COMPONENTS.md](../research/ESP32-REFERENCE-FIXTURE-COMPONENTS.md): TI TPS563201, bare Bosch BME280, Omron G5V-1 5 V coil, onsemi MMBT2222ALT1G with a 330 Ω base resistor and 100 kΩ base-emitter pulldown, and onsemi MMSD4148T1G coil suppression. The [Omron datasheet](https://omronfs.omron.com/en_US/ecb/products/pdf/en-g5v_1.pdf) specifies a nominal 30 mA 5 V coil and 1 A / 30 VDC contact rating under stated conditions. Contacts are restricted to low-voltage DC and the fixture does not route mains. A native schematic must map the exact package pins and pass ERC/DRC before firmware mapping can be treated as hardware-derived. Check module pinout and power/layout constraints against the [ESP32-S3-WROOM-1 v1.8 datasheet](https://documentation.espressif.com/esp32-s3-wroom-1_wroom-1u_datasheet_en.html) and [Espressif schematic guidance](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html).

The generator supports this fixed fixture only. For a safe reproducible validation run, `.github/workflows/esphome-reference-validation.yml` runs the official, version-tagged ESPHome 2026.10.0 container with generated placeholder secrets and invokes `esphome config`. The workflow is gated so it does not send firmware to a device; config validation does not prove the native netlist or relay behavior. A local ESPHome install is not assumed, and no host toolchain was installed.

## Home Assistant and deployment boundary

Use ESPHome's native API and standard HA integration path: after user-approved installation, the device can be discovered through mDNS or manually added with host/port and encryption key. The native API defaults to TCP 6053. Provide setup guidance and let the user complete pairing. Do not use HA internals to create an ESPHome config entry, or treat REST as a firmware deployment API. Any later HA companion should be optional and use documented config flow, auth and diagnostics conventions; HA's own MCP server exposes selected HA entities/actions but is not a firmware generator. ([HA ESPHome integration](https://www.home-assistant.io/integrations/esphome), [ESPHome API](https://esphome.io/components/api/), [HA config flow](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/), [HA MCP](https://www.home-assistant.io/integrations/mcp_server/))

First release order: downloadable YAML, local CLI validation/compile, then an approved handoff to a configured Device Builder instance. Device upload/build deployment is later and requires target identification, configuration diff, backup and explicit approval. Never overwrite existing configuration without a backup and comparison. Do not store a long-lived HA token in Circuit; if a future connection requires auth, use documented OAuth and minimum scope. ([HA auth](https://developers.home-assistant.io/docs/auth_api/), [REST](https://developers.home-assistant.io/docs/api/rest/))

## Conclusion

Make the first firmware result a transparent starting configuration whose provenance and unresolved choices are visible. The safe success condition is valid YAML for a known version and board profile, with the user still in control of credentials, deployment and hardware assumptions.
